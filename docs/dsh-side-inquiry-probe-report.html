五条核心结论

结论 1 · 定位级

缺口是「返回通道」，不是「执行能力」。 隔离执行 DSH 早就有（子代理 / dispatch）；你要的是把结果是否进入主线上下文变成一个独立可控的开关。 现有两种通道都是「必然回注」的变体：工具结果立刻全文回注，子代理延迟单条回注。

结论 2 · 框架级

第一册的五个旋钮里没有这一维。 D1 控制权 / D2 生命周期 / D3 通信拓扑 / D4 上下文策略 / D5 失败恢复——全部在描述执行端， 没有任何一维描述「顶点产出如何回到父上下文」。D4（spawn vs 独立会话）管的是顶点的输入从哪来， 不是顶点的输出到哪去。→ 需要新增 D6 回注策略（Echo Policy），见 §7.3。

结论 3 · 竞品级

ThoughtDAG 是这条需求轴上走得最远的实现，但它把「顶点」做成了模型调用而不是子代理。 它的四条原则——显式检索不自动注入、线即上下文、排除而非删除、给指针而非给内容——每一条都直击你的需求。 它缺的恰恰是团队派有的东西：名册、状态、生命周期、可管理的身份。见 §3。

结论 4 · 机制级

「不污染」与「可丢弃」是两个机制，必须分开做。 前者是准入控制（默认不回注即可，靠不调用写入原语实现）；后者是事后收容（已进入上下文的内容要能被遮蔽）。 现有实现常把两者都叫「删除」，于是两边都做不好。→ 见 §2.3 与 §7.5。

结论 5 · 落地级

它应该是 concourse 图上的一个新顶点类，而不是第二个插件。 探针与团队成员的差别只在三个属性上：lifecycle: ephemeral、 echo: handle、以及一条指向父顶点的上下文边而非通信边。 其余（名册、状态、预算、模型定档、审批、闸门）与 §7.6 既有机制完全复用。

2.1 · 原话拆解

思维导图与子代理拓扑有本质上的相似之处，从产品需求角度出发，本质上就是会话的中途想要查询某些旁路信息，但又不想污染上下文，只想以子代理类似的状态返回一个摘要的信息，或者丢弃这个子代理信息。
#原话片段我的解读它排除了什么
1 会话的中途 触发点在当前会话内，不切走、不新开标签页、不打断主线。 排除「另开一个会话去问」——那本来就是隔离的，痛点正在于要来回切。
2 某些旁路信息 与主线任务不必相关的信息：查一个 API、确认一个事实、看一眼某个文件为什么长这样、核一个数字。 排除「子任务分解」——旁路信息不是主线目标的组成部分，它可能用完就与主线无关。
3 不想污染上下文 硬约束：查询过程的中间产物（工具输出、试错、长文件）绝不进主线；连结论默认也不进。 排除「起个子代理然后把结果贴回来」——那仍然进上下文，只是量小一点。
4 子代理类似的状态 它要可被看见、可被管理：在 UI 里像一个成员那样有一席之地（名字、状态、在跑/已完成），不是一个隐形的后台请求。 排除「纯函数式检索」——你要的是有身份的临时执行体，不是一次 search 调用。
5 返回一个摘要 返回物是提炼过的而非原文。token(探针产出) ≪ token(探针消耗) 是这条需求的量化形式。 排除「把原始检索结果丢回来让主模型自己读」。
6 或者丢弃 摘要的存续是可选的。人（或模型）可以事后判定「这条我不需要了」并让它从主线消失。 排除「只读不写、过了就过了」——丢弃是一个显式的、事后可执行的动作。
最容易混淆的一点

第 3 条（不污染）与第 6 条（可丢弃）是两个不同的机制，必须分开设计：

· 不污染 = 准入前阻止内容进入上下文 → 靠「默认不回注」实现
· 可丢弃 = 准入后把已进入的内容从模型视野移除 → 靠 compaction / shadow 实现

现有实现里这两件事经常被同一个词「删除」混着说，结果两边都做不好—— 第一册里 nanmicoder 的 delete 是硬删，ThoughtDAG 的 archive 是排除而非删除，两者语义完全不同 第一册 §4.1 · ThoughtDAG lib/graph.ts / slices/nodes.ts。

2.2 · 五个可验证判据

把上面的解读压成验收条件（Acceptance Criteria）。后面每一节的设计取舍都回到这五条来判。

编号判据怎么算通过
AC-1旁路过程的零污染一次探针从发起到结束，主会话上下文长度不因它的探索过程而增长。可验证形式：探针跑掉 5 万 token，主线增长 0。
AC-2摘要在默认档位也不自动进入探针完成后，默认配置下主模型并不知道摘要内容；它只知道「有这么一条，地址是 X」。这一点必须与「子代理默认回注」形成对照。
AC-3模型可按地址主动取回主模型能通过一个工具（按 handle 取回）把摘要读进上下文——且这次读取是它自己的决定，不是系统的。
AC-4人可丢弃，且「遮蔽」与「删除」可区分UI 上有丢弃动作；丢弃后模型看不到该内容；遮蔽态在 UI 上仍可查、可恢复，硬删才有不可逆语义。
AC-5一等公民的呈现与晋升通道探针在 UI 里的呈现形态与团队成员一致（同一份名册、同一套状态徽章），并可「提升」为常驻成员——从旁路变成主线。
AC-5 是被低估的一条

「或者丢弃」的对偶是「或者留下」。一个旁路探针如果答得好，人的自然反应是「这个别丢，它以后还有用」。

这意味着探针与团队成员之间必须有一条双向的晋升 / 降级通道：探针 → 常驻成员（保留身份与记忆），成员 → 用完即弃。 这条通道在现有所有实现里都不存在——第一册 §7.3 的推论说得很清楚：「任务型」与「常驻型」被各家焊死在实现里。

缺口的准确表述

DSH 现有的两种通道是「必然回注」的两个变体：

· 工具结果 → 立刻、全文回注
· 子代理 → 延迟、单条回注

你要的是第三种：「默认不回注，按地址可回注，可遮蔽可丢弃」。
这不是现有两者的参数调整，而是一条新的返回通道。

补充一个刚查到的事实：这条新通道的人类侧入口已经有人做出来了—— §5.3 的划词解读把 AC-1 与 AC-2 做到了生产级（只注入 webServer 和 llm，根本不碰主会话）。 但它没有 AC-3 的取回口、没有 AC-4 的丢弃、AC-5 也只是"升格成一个新会话"而不是"提升为同一份名册里的成员"。

所以缺口的准确表述要再收一次：不是"通道不存在"，而是"通道有了，闭环没有"。 这个修正让需求更硬——我们不必论证可行性，只需要论证为什么闭环必须做在顶点层而不是交互层。

2.4 · 思维导图 ↔ 子代理拓扑：你那个比喻的落点

你开口第一句就是「思维导图与子代理拓扑有本质上的相似之处」。这个判断是对的，而且比"相似"更强——两者是同一种结构的两个投影。

思维导图一侧子代理拓扑一侧在本需求里统一为
一个节点 = 一个问题一个顶点 = 一个执行单元探针 Probe
一条连线 = 喂给这个节点的上下文一条边 = 通信 / 可见性信道上下文边（仅决定该探针能看见什么）
节点正文 = 模型对这个问题的回答顶点产出 = 子代理的最终消息摘要 digest

节点标题顶点的 role 名句柄 handle（模型按地址取回）
分支随思考即兴长出来顶点动态派生探针的即时创建（无需事先编排）
这个同构在代码里已经被证明过一次

ThoughtDAG 的项目自述是一句话："Wires are the context"（线即上下文）。它的 buildContext 做的就是把图上能走到的连线按固定顺序走一遍，拼成这次请求的 prompt——材料在前、虚线引用块、实线主干链、问题最后 src/store/context-builder.ts:208-375。

也就是说：思维导图不是"像"子代理拓扑，它本身就是子代理拓扑的一种 UI 投影——只不过 ThoughtDAG 把"顶点"实现成了模型调用，而不是子代理。

于是定位就清楚了：要的不是合并两个东西，而是一次正确的投影

4 · DSH 平台原语盘点

这一章回答唯一重要的问题：你要的这条通道，DSH 今天给不给？ 结论先行——给。而且比预想的完整：既能做到"彻底不进父上下文"，也能做到"单条遮蔽且不删原文"。

划词解读把"旁路可以存在、可以默认不回注、可以由人显式升级"这件事验证到了生产级。 但它止步于交互——没有一个可以寻址、可以被编排、可以被丢弃的实体。

换句话说：它是一条能用的通道，我们缺的是通道上的顶点。 这反而把 §7 的定位钉得更准了——我们要做的不是再写一个"划词解释"，而是让旁路变成图上的一等对象， 顺便把它的入口形态（划词、浮出、小窗、升格）直接借过来。

6 · 设计空间：七个正交维度

在给出具体规格之前，先把「旁路执行单元」这件事的设计空间摊开。 下面七维彼此独立——现有实现之所以看起来五花八门，多半是因为它们把七维中的好几维绑在了同一个端点上 （与第一册 §7.3 发现的问题同源）。

怎么读这张表

每一维列出可选端点，然后回答同一个问题：「选这一端的代价是什么？」 没有免费的选择，所有"看起来更好"的端点都在别处付账。

6.1 · 维度一：上下文隔离度（输入侧）

6.2 · 维度二：结果回注策略（输出侧）决定性维度

这就是本册提出的 D6。它是整条需求的重心，也是最容易被忽略的一维—— 所有人都在优化"怎么算得更省"，没有人优化"算完了怎么还给对方"。

端点做法代价
自动全文回注
现状		产出直接作为消息进入父上下文。上下文不可控。这是当前所有子代理/团队实现的默认行为，也是你要解决的问题本身。

6.3 · 维度三：可见性

端点做法代价
主对话流内可见像一条消息那样出现在时间线上。占视觉空间，且用户会下意识把它当"对话的一部分"来读。上下文纯净时它反而扎眼。
侧栏折叠只在一份名册里，需要时展开。用户会忘记它的存在。这是所有"侧边栏功能"的通病。
完全不可见仅落盘什么都不显示。不可审计。出了问题无法解释"这条结论哪来的"。

6.4 · 维度四：生命周期与归属决定性维度

端点做法代价
一次性即焚答完就结束，不可续聊。追问要重头来。旁路问题经常是"看了一个答案后想再问一句"，即焚会让第二次提问重复第一次的全部成本。
保留可续聊探针是一个持久会话，可以接着问。需要身份、状态、恢复能力。成本从"一次调用"升级为"一个资源"（要管生命周期、要管清理）。
提升为一等子代理从旁路单元直接变成团队成员。需要两条生命周期之间的状态转换（摘要/溯源要能迁移成初始记忆），且有配额与审批的含义。
降级回探针用完了就把成员降回即焚。反向转换同样要定义：哪些记忆丢掉、哪些保留、谁来决定。
为什么这一维是决定性的

它决定了这个东西是"一次调用"还是"一个资源"。而"一次调用"与"一个资源"在产品上的差别是巨大的： 前者不需要名册、不需要状态、不需要配额；后者全都要。

你原话里的「以子代理类似的状态」已经表明答案是资源——否则你不会用"状态"这个词。 这也正是它和"一次只读检索"的分界线。

6.5 · 维度五：触发方

端点做法代价
人显式提问用户自己开一个旁路问题。人要意识到"这件事我不想让它进主线"。多数人不会这么自觉，于是照旧污染。
模型自主发起模型判断"这该走旁路"。可被滥用：把主线任务偷偷外包，或把本可直接答的问题拖成一次昂贵探索。必须有配额与"不得作为交付"的硬约束。
系统建议检测到"这个问题与当前任务不相关"时提示。误报会打断心流。只能建议，不能自动执行。

6.6 · 维度六：丢弃语义

见 §7.5 的四级。这里只补一个设计判断：

「丢弃」必须与「删除」分开命名

把所有语义都叫 delete 是现有实现的通病，结果是用户不敢用这个功能—— 因为"删除"听起来永久且危险。

而实际上，用户想做的百分之九十是"让它别再占用我的注意力与上下文"， 这既不需要销毁数据，也不需要不可逆。把默认动作做成可逆的遮蔽，是这个功能能不能被日常使用的关键。

6.7 · 维度七：成本与配额

端点做法代价
混入主线记账探针消耗算进当前会话。用户无法判断"这次探索值不值"。成本一旦不可见，就不可能被优化。
单列记账探针成本独立显示。需要额外的计量与 UI。但这是唯一能让"旁路"变成可管理决策的做法。
无并发上限想开多少开多少。模型自主发起时可能瞬间开十几个，成本失控。
有并发与频率上限默认同时 3 个，模型侧另有限额。复杂任务可能被卡住。缓解：上限可配，且人的操作不受限、只限模型自主发起。

7 · 需求文档：旁路探针

本章把前面所有分析收敛成可实施的规格。核心只有两样东西：一个新顶点类，一个新旋钮。 其余全部复用第一册既有机制——这是本方案能不能落地的关键，凡是需要"再造一套"的地方都是设计错误。

7.1 · 定位

定义

旁路探针（Probe）是在当前会话内即时创建、上下文隔离、产出默认不回注、可遮蔽可丢弃的临时执行单元。 它由一个旁路问题触发，交回一份摘要，并留下一个可寻址的句柄。

7.1.1 · 三条边界

它很容易和三个近邻混淆，必须先把边界划清，否则规格会膨胀成"再造一个团队插件"。

它不是为什么判据（越界了就说明设计错了）
不是团队
区别于 concourse 成员		 探针不组队、不派活、不建任务板、不承担 task DAG 的任何节点。它回答一个问题就结束，不存在"协作"。 如果规格里出现了"探针之间通信"或"探针的任务依赖"，就已经跑偏。
不是任务分解
区别于子任务		 探针的产出不是主线目标的组成部分。主线不需要它也能完成——这正是它能被随意丢弃的原因。 如果需要把探针结论写进计划才能继续，那它本该是一个普通子代理或任务节点。
不是检索工具
区别于 grep / search / why_find		 探针会推理：可能多次调用工具、读长文件、试错、综合判断。它比一次查询重，比一个完整子代理轻。 如果它只做一次确定性查找，用工具就够了，不必起探针。

7.1.2 · 它与三者的分工

单元解决的问题产出成本量级返回方式
工具取一段已知位置的信息原文（可能落盘+路径）百 ~ 千 token同步进上下文
探针搞清一件与主线无关的事摘要 + 句柄千 ~ 万 token不回注，可拉取
子代理 / 成员完成一个主线目标的组成部分成果 + 可续聊会话万 ~ 十万 token异步推回上下文
这条分工线的位置是本次调研最重要的产出之一

现有生态是哑铃形的：一头是极廉价的工具调用，一头是极重的子代理/团队成员， 中间那一档「我只想花几千 token 搞明白一件事，然后多半就扔了」没有对应物。

人的直觉早就知道这一档存在——它就是你会随手在搜索引擎开一个标签页、查完关掉的那个动作。 当前的 DSH 里，这个动作要么退化成一个工具调用（把垃圾拉进上下文），要么升级成一个子代理（结果赖着不走）。

一句话记住差别

子代理的返回是推送（push），探针的返回是拉取（pull）。

7.2.1 · 为什么现有实现全是推送

这不是任何一家偷懒，而是它们的返回通道在底层就是「给对方发一条消息」，而在 agent 生态里消息等同于进入上下文。

实现返回通道的底层原语结果
官方 dsh-experimental-agent-team 持久 peer mailbox，投递即 Steer 唤醒 必然进上下文
@nanmicoder/dsh-agent-teams 成员邮箱 + 调度器 kickMember 必然进上下文
DSH 原生 subagent / dispatch 子会话结束 → 最终消息落回父会话 必然进上下文
唯一做过「不推送」的实现，恰恰不是团队派

dsh-thoughtdag 的 why 层四工具（why_check / why_file / why_find / why_recall）是只读、显式、按需调用的， 其作者原话是："Retrieval is explicit; matching history is not automatically injected into every prompt." DEV 文章《Before Your Coding Agent Edits a File, Let It Ask Why》

也就是说：「不推送」这件事在 DSH 生态里已经有人验证过可行，只是它做在「检索」上，没有做成一个执行单元。 本方案要做的，是给这条已经存在的通道配上一个子代理级别的执行体与一等公民的身份。

7.3 · 第六旋钮 D6：回注策略（Echo Policy）

第一册 §7.3 的五个旋钮解释了你"领队中心式 vs 扁平分布式"的困惑。现在这条需求暴露了那个框架的第六个空白维度。

7.3.1 · 先澄清：D6 与既有 wake 不是一回事

第一册 §7.2 的边属性里有 wake（never / on-reply / always，默认 never）。 它看起来很接近，但作用在另一个时刻、另一个方向：

属性作用时刻方向回答的问题
wake 消息投递时 发送方 → 接收方 「这条消息要不要把对方叫醒？」——防的是打扰与回声风暴。
echo 产出完成时 产出方 → 父上下文 「这份产出要不要进入对方的上下文？」——防的是污染。
为什么必须分成两个

官方 mailbox 的失败恰好证明了它们是两件事：官方做到的是「投递即唤醒」（wake 恒为 always，没有静默档）， 但它从来没有考虑过 echo——它的每条消息都必须被对方读到。

反过来，一个机制完全可以做到 wake: never, echo: none：消息静静放进对方邮箱，对方下次自己扫； 也可以做到 wake: never, echo: full：不叫醒你，但结果直接写进你上下文。两者独立，四种组合都有意义。

7.3.2 · D6 的四档取值

取值语义模型怎么拿到内容适用
full 全量回注 产出作为一条消息直接进入父上下文 当前子代理 / 团队成员的现状。探针不用这一档
summary 摘要回注 只把摘要作为消息推进来，正文丢弃 后台补充信息：希望模型一定看到，但不要看全
handle 只留句柄
本方案默认		 上下文里只出现一个地址（p3 之类），摘要与正文都留在探针的存储里； 模型显式调用取回工具才读进来 探针的默认档——满足 AC-2 / AC-3

7.3.3 · 通知档位：一个必须单独暴露的子属性

把 D6 设成 handle 之后，立刻撞上一个新问题：连"有这么一条"这个事实本身，也是上下文里的字符。 AC-1 要求零污染，AC-3 要求模型能主动取回——两者在这里直接冲突，必须显式取舍。

通知档完成时写入上下文的内容成本模型如何发现句柄
silent 什么都不写 0 token 只能靠一个只读枚举工具（如 team_status）主动扫。严格满足 AC-1，但模型不知道要去扫。
tick
默认		 一行轻量通知：探针 p3 完成 · 主题「XXX」· 未回注 约 15–25 token 通知里带句柄。模型知道"有过这么一件事"，但不知道内容——这正是 AC-2 的准确语义。
inline 摘要正文 数百 token 退化为 summary 档，不再是探针语义。
为什么默认选 tick 而不是 silent

AC-1 的直觉是"零污染"，但零污染要付一个真实代价：模型永远不会主动去枚举它不知道自己有的东西。 一个 silent 探针在实践中的命运是"跑完就没人记得"，等于白花钱。

20 token 换来"模型知道该不该去取"是一个极好的交易—— 相比它可能省下的成千上万 token 探索量，这是四个数量级的杠杆。

但如果你的目标真的是极端严格的上下文纯净（例如逐 token 复现的调试会话），silent 档必须保留且可用。

一个必须写进规格的量化判据

否则"不污染"会变成不可验收的口号。建议钉死两条：

① 回注比：echo_ratio = 回注进父上下文的 token / 探针消耗的总 token。 handle 档的 echo_ratio 应 < 1%；tick 档实测约 0.1% 量级。

② 回注上限：即使模型调用了取回工具，单次取回也应有硬上限（建议默认 2,000 token，可配）， 防止"取回"变成新的污染入口。

7.4 · 生命周期状态机

探针与团队成员最大的差别在生命周期：团队成员至少活到任务结束，探针可以在成立的下一秒就被否定。 这要求把"存在"与"被使用"彻底解耦——探针的产物存在，不等于它出现在上下文里。

动作人模型系统自动约束
创建探针是是否模型自主发起必须受配额约束，见 NFR

遮蔽（shadow）是有条件否默认只有人能遮蔽；模型自我遮蔽需显式开启，因为它可以借此掩盖自己的错误
恢复（un-shadow）是否否恢复权归人
晋升（promote）是建议否模型只能建议，不能单方面把临时单元变成常驻成员（会消耗配额与预算）
硬删（discard）是否TTL不可逆，必须二次确认；系统 TTL 清理需可配且有台账
为什么"模型不能自我遮蔽"

遮蔽的本质是"我说过的话，现在我不再让你看见"。如果模型可以对自己的产出做这件事，它就获得了一种 不留痕迹地否认自己结论的能力——这在需要审计的多智能体协作里是不可接受的。

人做遮蔽是编辑（用户本来就是对话的编者），模型做遮蔽是隐瞒。两者动机不同，权限必须不同。 第一册 §7.5 的闸门思路在此复用：权威判定放在收件箱准入，而不是放在发送端。

模型自主发起探针：这是双向的

AC 里没写，但值得单列：探针的触发方有两类——人显式提问，和模型在推理中发现"我需要查点旁路的东西"。 后者才是这个能力的上限所在：模型自己意识到"这个问题与当前主线无关，我不该把它拉进来"。

但它同时是最危险的：模型可以借此把主线任务偷偷外包给探针，造成"看起来答完了、实际上是旁路产物"的假象。 约束应当是：探针的产出永远不能作为主线任务的完成依据——它只能被取回作为参考，不能充当交付物。

7.5 · 丢弃语义四级

"丢弃"是本需求里被说得最含糊、也最容易被实现坏的一个词。它至少有四层含义，每一层用不同的机制、担不同的风险。

级别语义做了什么可逆承担的风险
L1 不取回
默认，零动作		 什么都不做。摘要停在 done，句柄自然过期。 可 无。这是唯一零成本、零风险的丢弃——因为它压根没进来过。
L2 遮蔽
推荐默认		 内容已经进入过上下文，现在对模型不可见；UI 仍可查、可恢复。 可 模型的历史认知与当前可见内容出现不一致：它可能记得自己读过，但看不到原文。需要遮蔽标记来显式告知。
L3 撤销采用 把摘要从上下文移除并回到 done 态；等价于"当作从没取回过"。 可 同上，且比 L2 更彻底——连"我取回过"这件事也不留。审计上更弱。
L4 硬删 产物与句柄一并销毁，仅审计台账留一条记录。 不可 不可逆；若它已 adopted，会出现上下文里引用了不存在的产物的悬空引用。
核心建议：默认丢弃 = L1，显式丢弃 = L2

L1 是免费的，应当成为默认。绝大多数探针的正确归宿就是"跑完、留个句柄、没人取、过期"。这条路径不需要任何机制。

当人已经取回（adopted）之后反悔，用 L2 遮蔽而不是 L4 硬删。 理由有两条：

① 可逆性保护的是用户的后悔权。上下文里的一句话删掉容易，但"我到底看过什么"这个信息一旦丢失就再也恢复不了。

② 硬删会制造悬空引用。如果后续对话引用了已删内容，模型与用户都无法回溯——这正是第一册反复强调的 "排除而非删除"（ThoughtDAG 的 archive 语义）在单条粒度上的落地。

丢弃必须留痕

L2 / L3 / L4 都要写一条审计事件（谁、何时、丢弃了哪个句柄、当时的级别）。 否则会出现一个反直觉的坏结果：越是被丢弃的内容，越查不到它曾被丢弃。

这与第一册 §7.6 的决策台账是同一套要求——ThoughtDAG 之所以在第三方评测里拿到 audit_log 这一项， 靠的就是"每次语义变更都写事件，且事件日志本身 append-only"。

为什么不复用 team_assign

一个自然的想法是"探针就是派给一个临时成员的普通任务，复用 team_assign 即可"。这条路要放弃三样东西，正是本需求的核心：

① 探针的产出不进入任务板（AC 里它没有依赖边、没有验收契约）——复用 assign 会把它塞进 task DAG；
② 探针的产出默认不回注——复用 assign 会走成员的返回通道，那是 push 的；
③ 探针没有质量门禁的必要（旁路信息不需要 review 通过才能交付），复用 assign 会白白套上验收流程。

结论：它们共享执行底座，但属于不同的语义层——任务是对主线的承诺，探针是对自己的备忘。

D-4模型能否自我遮蔽不能（FR-6.3）。理由见 §7.4.3。
D-5探针是否自动重试不重试（D5 固定为"无恢复"）。旁路问题失败不影响主线，自动重试会蒙掉成本。
D-6是否复用 team_assign不复用，新增 team_probe / team_peek。理由见 §7.6.3。
D-7通知档默认tick（约 15–25 token），而非 silent。理由：silent 在实践中会让探针白跑。
D-8与第一册的优先级探针先行。适用面更大（T0 即可用）、成本更小、且不依赖团队拓扑是否建成。
D-9探针的上下文输入默认是什么隐藏参考上下文（单向），而非完全干净的 spawn。依据：Cursor Side Chats 已验证此形态（§5.2）， 且单向性使"污染提前"的顾虑不成立。spawn 保留为可选降级档。
D-10零回注的实现路径主路径 ctx.subagents.start() 不返回结果；提炼段用 ctx.llm.stream()（会话无涉）。 见 §4.4。不采用 agent.inject 作为零回注手段——它进上下文。
D-11遮蔽的实现路径优先用 SurfaceOp.replace 单节点替换（原文不删、UI 可见）； 不依赖 ctx.compaction，因为它在宿主平面不可用。见 §4.3。
