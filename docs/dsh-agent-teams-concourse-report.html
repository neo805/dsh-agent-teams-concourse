本版依据你的 8 + 1 条评议做了架构级修订，全部决议记录在 §9.2。四处最实质的变化：

① 新架构层：虚拟拓扑（§7.1.2）。官方底座物理上已是完全图， 因此复合树状拓扑从完全图上剪出来即可，无需真实嵌套——执行底座恒为一层，多层嵌套的成本爆炸从结构上消失（§7.2.4）。

1 · 摘要与核心结论

一句话结论： agent-team 品类正在被官方收编；真正空白的不再是"能不能组队"，而是 组织拓扑的表达能力、逐成员的模型定档、 通信的硬约束、以及反拟人化的高密度 UI—— 这四件事恰好就是你提的痛点，也恰好没有一家做到。

而其中最关键的一条已经找到答案：官方底座物理上已是一张完全图（任意成员间可达的持久邮箱）， 因此"多层复合树"不需要真实嵌套去搭建——它可以从完全图上把边剪出来。 这就是本方案的核心架构：虚拟拓扑。

五条核心结论

结论 1 · 定位级

官方已内置 Agent Teams 子系统，且明确不支持嵌套团队。 @deepseek-ai/dsh-experimental-agent-team@0.2.0-rc.2 提供了持久点对点邮箱、带 CAS 的共享任务 DAG、不变式校验与投影—— 这些"最难做对"的部分官方已经做扎实了。但它的 roster "扁平且不可变"，官方原话： "不支持嵌套 Team、重命名、删除或名字复用"，并把 "嵌套 Team"列为未承诺的探索方向。

→ 新插件不应重造邮箱与任务板，而应复用官方底座 + 补上官方明确缺失的那一层。

结论 2 · 你列出的 5 个竞品全部落在两个孤立点上

层级派（nanmicoder）是单层单队长星型——memberMaxDepth 默认 0，成员连一个后代都拉不起来； 扁平派（team-rooms）是无层级的对等网状。 官方是 Implicit-root 单锚点。

你要的 tier1 与 tier2 之间的连续谱，以及"总领队下挂子团队、子团队内部扁平"、 "2~3 个总领队并列且互通信"——没有任何一家实现。 这不是巧合，是因为所有实现都把拓扑写成了代码常量。

结论 3 · 你的审美与交互痛点，在代码里逐条得到确证

① "小虎鲸"属实：team-lead-v2.png 是戴船长帽的蓝鲸、member-engineer-v2.png 是护目镜+扳手，共 15 张 256×256 PNG。 代码层零 emoji——拟人化全部由位图承担。
② "侧栏信息杂乱"属实：单屏约 180 个数据点，且以 1 秒间隔全量轮询磁盘。
③ "成员间可直连"但没有任何速率/跳数/场景约束——回声风暴的机制性前提是存在的。

结论 4 · "审批太多"的根因不在 UI，在协议文本

实测：nanmicoder 插件的 UI 强制确认只有 4 处，典型大任务用户只需点击 1–3 次。 真正制造审批疲劳的是 captain 协议（system prompt 层）——它要求"计划必须等用户批准""部署必须显式确认"等， 而 reassign / amend / remove_member / delete 这些破坏性操作在代码里反而没有任何确认。

→ 这说明审批强度与破坏性错配：该管的没管，不该管的层层设卡。新插件的目标是"一次审批定全局"，而不是"取消审批"。

结论 5 · 你的 tier 直觉是对的，且可以用"虚拟拓扑"形式化

把你的 tier0/1/2 扩展成 6 级拓扑谱系（T0 / T1a / T1b / T1.5 / T2a / T2b）后， 它不再是一根轴上的刻度，而是一张图：顶点 = 执行单元，边 = 开放的通信信道。

而这张图不需要"搭建"，只需要"修剪"——官方底座已经提供了完全图， concourse 声明开放边集即可把它裁成任意复合树状外观。 执行底座因此恒为一层，多层嵌套的成本爆炸问题从结构上消失。 拓扑一旦成为数据，"各种组织架构都有可能"就自然成立。

结论 6 · 组织形状与用户交互被解耦了

本方案把"内部拓扑有多复杂"与"用户面对几个窗口"彻底分开： 默认单会话、零新会话、用户只与唯一领队对话、拓扑上限 T1.5； 只有当你自己已经有多个独立会话、并主动要求它们协作时，才把它们拉进来， 并选择其角色是子节点（保持 T1.5）还是平级领队（升级 T2a）。

同时，子节点不具备建队能力——审批因此不可能被下级打断， "一次审批、运行期零审批"由能力剥夺而非流程约定来保证。

实现细节 · 三个最重要的架构事实

① attempt_id capability 模型（防串改的地基）

每次任务领取发放一个 randomUUID() 作为一次性执行凭据，写入团队状态并只发给当前 owner。 转派时先清 attemptId + 生成 handoffId、置 reassigning， drain 子激活后再开新代际；迟到的更新按代际被拒。 lib/state.js:146-186 · lib/tools.js:1321-1326, 1577-1582

② 调度是事件驱动，且必须先有 live captain

ctx.on('agent/status') 的 idle 边触发 kickMember； 成员只领"指派给自己"或"完全未指派"的就绪任务，绝不抢别人的 lib/scheduler.js:116-122。 队长会话不在线则完全不调度 scheduler.js:222-224。 parkedAttempts 保证只有冷进程启动才允许一次自动恢复，避免无限重试。

衍生缺陷

用户关掉对话页/切换会话后团队静默停住，界面上表现为"任务一直 pending"。 README 声称"关闭标签页不会停止团队"，但队长会话本身必须还活着——这两句话在体验上会互相掩盖。

③ 质量门禁是"完成时审计"，不是写入拦截

任务要 completed 时强制校验 acceptanceResults / commandsRun / changedPaths； changedPaths 每个路径必须判为 in_scope 才放行； review/requirements 只有 verdict=pass 且无未解决 high/blocker findings 才能完成； 失败自动生成 repair + 下一轮 review，并把仍 pending 的下游依赖重挂到新终局门。 lib/quality-gates.js:347-406, 579-649 · lib/tools.js:2330-2338

诚实边界

README 自认："第一版范围控制是完成时审计，不是 host 写入拦截"。 即：越界写入只能事后判"任务不能完成"，无法阻止写入发生。

四个对你需求影响最大的局限（均为代码确证）

局限 1 · 不支持多层嵌套团队 / 子队伍 直接对应 U-9/U-10/U-11

memberMaxDepth 默认 0：成员不能创建任何后代代理， installMemberDelegationGuard 沿父链遍历，一旦发现当前 agent 是成员且 depth > maxDepth 就抛错 lib/index.js:83 · lib/members.js:607-654。 即便手工把 memberMaxDepth 设为 1，也不能形成子队伍——成员的 agent_teams_create 被 tools.restrict 拒掉，成员人格第 9 条明写 "你是 worker：不要创建或删除团队、不要转派任务、不要增删成员" lib/capabilities.js:82-85 · lib/members.js:467。

结论：它是单层、单队长的星形结构。不存在子队 / 嵌套队 / 多队长。

局限 2 · 模型/推理强度不能按任务逐个指定 直接对应 U-5

TeamTask 类型里没有任何 model/provider 字段。 模型只在成员维度解析；approve 之后路由冻结——模型在 approve 时被重新解析并写死进 team.json， 进入 running 后 update_member 被拒。 UI 上任务显示的模型是从负责人反查的（memberModelRoute(roster.find(m => m.name === task.assignee))）， 不是任务自身的属性 lib/types.d.ts:79-134 · lib/members.js:198-254 · lib/tools.js:464-474, 358-360 · lib/snapshot.js:107。

局限 3 · 成员之间可以直连通信，但没有任何硬约束

7 · 需求文档 · dsh-agent-teams-concourse

7.1 · 定位与设计原则

一句话定位

dsh-agent-teams-concourse 是 DSH 的组织层： 它把"谁和谁能通信、每个执行单元用什么模型与思考强度、任务在层与层之间如何流动"变成可编辑的一等数据， 用一次计划审批换运行期零审批，用几何符号换掉一切拟人化元素。

"concourse"取"汇流"之意——多条协作路径在此汇合，而不预设某一种组织形状。

7.1.1 路线取舍：为什么是"分层"而不是"自建"或"寄生"

实测结论：官方 ctx.agentTeams 已经把持久点对点邮箱、带 CAS 的共享任务 DAG、 不变式校验、会话投影、崩溃恢复对账做扎实了——这恰恰是最难做对的一半。而它的 roster 扁平且不可变、明确不支持嵌套，且官方把"嵌套 Team"列为未承诺方向。

路线做法优点致命风险取舍
A · 独立自建 自己实现 roster / mailbox / 任务 DAG 完全可控，不绑实验 API 重造轮子；且与官方 scoped 工具同名冲突（send_message / list_agents / wait_agent / interrupt_agent / team_task_* 已被占用） 否
B · 完全寄生 只做官方之上的 UI 与建议 最省力 无法补官方缺的"嵌套团队"——服务层根本不支持，UI 层无从表达 否
C · 分层 推荐 复用官方 mailbox / DAG 作底座，在其上实现 concourse 层：拓扑投影 · 任务树映射 · 模型定档 · 通信约束 · 自有 UI 不重造轮子；增量精准落在官方明确缺失处 官方为 experimental、无稳定性承诺 → 必须用薄适配器隔离 推荐
路线 C 的硬前提：适配器必须薄，且必须能降级

实测表明官方契约没有任何 @deprecated 标记（全库 grep 0 命中）， 官方包之间靠精确版本 pin（互相 0.2.0-rc.2，cordis ~4.0.4）。 这意味着没有编译期废弃信号，升级只能整栈对齐。

→ 因此 concourse 必须把对 ctx.agentTeams 的全部调用 收敛到一个 substrate.ts 适配模块，并对每个方法提供能力探测与降级路径。 当官方不可用时，concourse 降级为"自有任务图 + 不提供跨顶点邮箱"，而不是崩溃。

7.1.2 核心架构：虚拟拓扑（Virtual Topology）

本方案最关键的一条设计决定

官方底座在物理上已经是一张完全图：Implicit-root 的 Lead + 持久点对点邮箱， 使得任意两个成员之间、成员与 Lead 之间都存在可达的通信信道。

因此 concourse 不需要"建造"任何拓扑—— 它要做的是在这张完全图上显式声明开放边集，把完全图裁剪成任务所需的复合树状形状。

拓扑是"修剪"出来的，不是"搭建"出来的。这是本方案与品类里所有其他实现的根本差别。

由此推出的第一性质：执行底座恒为一层

所有顶点都是该会话的直接子代理，派生深度恒为 1。 "层"（layer）只是对顶点施加的权限与可见性标注，不是真实的派生嵌套结构。 树形外观由开放边集决定，而非由调用栈决定。

这直接兑现了你的第 1 条评议——多层嵌套的成本爆炸问题从结构上消失， 因为根本不存在多层。

7.2 · 拓扑谱系（tier 模型）

这是本报告的核心贡献，也是回答你 U-9/U-10/U-11/U-12 的形式化工具。

7.2.1 形式化：concourse = 完全图上的开放边集

官方底座提供一张物理完全图 Kn（任意两顶点之间都可达）。 concourse 的定义因此是一个带属性的有向图 G = (V, E)， 其中 E ⊂ Kn 是开放的通信信道集合——不在 E 里的边即被闸门关闭。

顶点是执行单元（在底座中全部是该会话的直接子代理），边是其上叠加的通信策略。 两者都必须带属性，否则退化成现有插件的"常量拓扑"。

关于"开放集 vs 关闭集"的一个澄清

你把它描述为"完全图，然后关闭一些通道"，这在数学上等价于"声明一个开放边集"—— 因为 开放集 = 完全图 − 关闭集。

两者只是叙述方向不同，但执行时的默认策略必须取"开放集"语义（即 deny-by-default），原因是失败模式不对称：

· 若默认开放、忘记关闭 → 出现计划外的通信通道（静默、难发现、直接构成回声风暴风险）
· 若默认关闭、忘记开放 → 投递被硬拒绝并留痕 → 用户立刻看见并修正

所以：底座的物理事实是完全图，concourse 的模型是开放边集，执行时 fail-closed。 三者说的是同一张图的三个层面。

7.2.3 默认形态与升级路径（会话加入）

默认规则：单会话内 ≤ T1.5，且绝不新开会话

在一个会话任务中布置 / 拉起的 agent team，默认全部在同一会话内完成，不创建任何新的独立会话。 用户只与唯一的一个会话（领队）直接沟通；所有其它顶点都是该会话的子代理，对用户不可见地运行。

默认拓扑上限为 T1.5。T2a 不会自动出现，必须由用户显式触发下述升级。

唯一的中途升级路径：加入已存在的独立会话

触发条件（必须同时满足）：

① 用户本来就已经有多个独立会话（它们先前各自独立工作过，不是本次任务派生的）；
② 用户显式表达"我要把这几个会话拉进同一个 team 协作推进"。

加入时可选择该会话的拓扑角色：

加入角色语义拓扑结果边
作为子节点 新会话成为当前会话（领队）的下级，向领队汇报 保持 T1.5 开放 leader ⇄ joined；joined 的横向边由策略决定
作为平级领队 推荐 新会话与当前会话具有平级的领队地位，各自带自己的子图，两个领队之间可通信 升级为 T2a 开放 leader ⇄ leader（mode: notify 或 request-reply，wake 默认 never）
三条必须守住的边界

① 加入的是"已存在的会话"，不是"新建的会话"。concourse 不提供"从零开一个新会话加入团队"的能力—— 那会退化成真实嵌套，并让用户面对第二个对话窗口。加入的对象必须是用户自己已经开着的会话。

② 升级到 T2a 需要重新走一次审批——但这是用户的主动操作（他自己说"要拉进来"）， 不是被系统打断的。这与 D-5 禁止的"子节点建队计划打断用户"是完全不同的性质。

③ 平级领队之间不互相指挥。T2a 的根间边只承载通报与协商， 不承载任务指派——任务指派一律沿树边向下。否则会出现"两个领队互相分派任务"的权限二义性。

7.2.4 为什么虚拟拓扑能遏制成本爆炸

这是你第 1 条评议里最有价值的判断。关键在于：虚拟拓扑把"递归派生"换成了"一次性声明"。

维度真实嵌套 concourse虚拟拓扑（本方案）
执行底座深度递归派生，深度无上界恒为 1（所有顶点都是该会话的直接子代理）
顶点数量来源运行时由各级 sub-captain 递归决定计划期一次性声明，开工前完全确定
成本可预测性差——分支因子逐层相乘，随深度爆炸好——成本 ≈ f(N 个顶点, 开放边数)，计划期即可算出
审批次数1 + 每个子团队各一次（违反 D-5）恒为 1；会话加入由用户主动触发，非系统打断
状态锁域每层一个 team lock，存在嵌套死锁风险单一锁域
恢复对账每层一套 provisioning 对账单一一套
投影 / 广播量每层各自广播完整 roster + 任务板一次投影（也顺带缓解了官方"全量广播"的已知缺陷）
拓扑形状由什么决定由运行时的派生结构决定由开放边集决定（纯声明）
一句话总结这一节

真实嵌套的成本来自"运行时的结构生长"——它是涌现的、不可预算的、需要逐层批准的。 虚拟拓扑把它替换为"计划期的结构声明"——它是枚举的、可预算的、一次批准的。

树是视图，不是机制。

回应评议第 3 条。把"多窗口"从默认路径里彻底移除——用户面对永远只有一个对话。

FR-2.3会话加入：唯一的拓扑升级路径

仅当用户已持有多个先前独立工作过的会话且显式要求时，允许把这些会话拉入本团队， 并由用户选择其角色：作为子节点（保持 T1.5）或作为平级领队（升级 T2a）。

实施约束：

· 加入对象必须是已存在的会话——不提供"新建会话再加入"
· 平级领队之间的边只承载通报与协商，不承载任务指派（任务指派一律沿树边向下）
· 被加入的会话在拓扑中标记 origin: joined，与 spawned 顶点在权限上区分

回应 U-11 与评议第 3 条。这是 T2a 的唯一合法来源，也正是"用户作为最高指挥官"这一诉求的落点。

FR-2.4单一审批闸门，且不可被下级打断

审批只发生在用户直接对话的那个会话里，且全局只有一次。 子节点不得拥有"创建团队"的能力，因此不可能在运行中弹出自己的组队计划要求二次批准。

唯一的例外是 FR-2.3 的会话加入——但那是用户主动发起的操作，不是被系统打断。

回应评议第 7 条。审批疲劳的根源是"审批点散布在多个层级"。本方案把审批收敛到唯一的、用户已经在看的那个会话，并用能力剥夺（子节点没有建队工具）而非流程约定来保证它。

FR-2.5不做真实嵌套 concourse

concourse 不允许在自身内部再创建 concourse。任何层级效果只能通过 §7.2.1 的开放边集裁剪来表达。

回应评议第 7 条，两条理由：
① 不必要——拓扑已是官方扁平形态的子集（虚拟复合树），真实嵌套不带来任何表达力增益；
② 不可接受——即便只做虚拟嵌套，它的初始化也会在运行中产生一次新的组队审批，打断用户已批准的总计划。

FR-2.6顶点数量与深度在计划期完全确定

开工前必须给出完整顶点集合与开放边集；运行期不得派生计划外的新顶点。超出预算或并发上限时在计划期报错，而非运行时失败。

成本预算化的前提（§7.2.4）。同时规避宿主 maxActiveSubagents 默认 8 带来的"跑到一半撞顶"。

7.4 · 模型与思考强度定档（回应 U-5 / U-6）

7.4.1 定档粒度：顶点级 + 任务级双层

每个顶点独立可设 model · reasoningEffort · toolFilter · tokenBudget · maxDepth · contextMode； 每个任务独立可设 assignee · 难度画像 · 期望产物。

7.5 · 通信硬约束（回应 U-7）

7.5.1 回声风暴成因分析

回声风暴 = 唤醒 → 推理 → 回复 → 唤醒对方 → 推理 → … 的正反馈。四个成因：

ID成因说明成本增长现状
C1自动唤醒放大收到消息即触发一轮完整推理随跳数线性六家全中
C2广播放大1 条广播 → N 个顶点各推理一轮并回复随成员数指数六家全无防护
C3无终止判定没有"对话已收敛"的概念；礼貌性回复本身制造下一轮不收敛六家全无
C4无预算约束成本事后才可见失控不可逆仅容量上限
实测确证的严重性

team-rooms 的 7 条硬约束全部是容量约束；官方 agent-team 只有 maxPendingMessagesPerMember: 64 一个容量兜底。 两者都没有速率限制、没有冷却、没有跳数、没有方向约束、没有静默判定。

且两者的投递语义都是"投递即唤醒"（team-rooms 的 agent.followup 无条件开新回合； 官方的 Steer 会冷恢复 inactive target）。 单轮扇出 = 发帖数 ×(成员数−1)；保留窗口剪的是历史，不是流量。

唯一真实的刹车是模型自身的收敛倾向与回合延迟（team-rooms 本机实测中位 25.7 秒/跳）—— 那是运气，不是机制。

7.5.2 硬约束清单（全部为硬拒绝，不是软警告）

A · 拓扑类 —— 谁能发给谁

FR-5.A1完全图上裁剪出开放边集（虚拟拓扑的落点）

底座任意两顶点间都可达；concourse 声明开放边集 E， 投递前校验 (from, to) ∈ E。违反 → 工具调用失败，不是警告。

执行时取 deny-by-default 语义：未声明即不可通信（理由见 §7.2.1 的失败模式不对称分析）。

这是"虚拟拓扑"的机械实现——复合树状外观不是搭出来的，而是从完全图里剪出来的。

FR-5.A2半双工可选

A→B 存在不蕴含 B→A。请求-应答模式声明为两条边并绑定 correlationId。

FR-5.A3跨边界闸门

跨越团队边界的边需显式声明 + 一次审批（计划期一次，不是每条消息一次）。

借鉴 team-rooms 的血的教训：它的 room_transfer_task 审批闸门只存在于工具外壳里，hub.assignTask 本身无闸门 → 导致 /room task assign 命令与 Web 交接按钮完全绕过审批。
因此：硬约束必须落在数据写入口（领域服务层 / invariant 层），而不是各个 UI 与工具入口。

B · 唤醒类 —— 最容易失控处

FR-5.B1wake: never 为默认 最高优先级

消息进邮箱，不触发对方新一轮推理；对方在下一个自然步点读取。

这是最强的防回声手段——它把"事件驱动"降级为"轮询驱动"，从根上消灭互相唤醒。代价是响应延迟上升，因此需要显式选择 on-reply 来换取低延迟（并接受相应的约束与预算记账）。

FR-5.B2唤醒预算

每个顶点在每个"回合窗口"内最多被主动唤醒 N 次（默认 1）；超出即降级为"投递不唤醒"，并在流水里留痕。

FR-5.B3广播降级

广播只入共享板，不唤醒任何顶点。要唤醒必须逐个显式定向。

针对 C2 指数放大。现有插件的广播等价于"向 N 个人各发一条会唤醒的消息"。

C · 终止类 —— 怎么算聊完了

FR-5.C1跳数 TTL

消息携带 hops 与 ttl；hops > ttl → 只记录不投递，并在板上标记 HOP_LIMIT。

FR-5.C2静默判定（quiescence）

某会话线程连续 K 轮（默认 2）无新增事实（纯确认 / 纯致谢 / 纯重述）→ 冻结该信道，后续消息只入板。

针对 C3。这是唯一能真正终止"礼貌性互推"的机制——因为礼貌性回复在内容上不携带新信息，可用启发式可靠识别。

FR-5.C3幂等去重

按 hash(from | to | correlationId | 内容摘要) 去重；重复投递直接丢弃并计数。

官方已实现"target 会话去重"（不重复投递），可直接复用；concourse 需要补的是内容级去重与统计可见性。

D · 预算类 —— 成本兜底

FR-5.D1通道预算

每条边 / 每个顶点可设 token 预算，超额熔断该边或该顶点，而非整个团队。

FR-5.D2全局熔断

concourse 级预算超额 → 暂停所有 wake ≠ never 的投递，仅保留人工恢复。

这样设计的原因：熔断后系统仍可被人类读取与干预，而不是整体瘫痪。

E · 可观测性（必需，不是可选）

FR-5.E1回声计数

统计每条边的 投递数 / 唤醒数 / 被去重数 / 命中约束数，在 UI 以一行"通信健康度"呈现（纳入 P3 单行总览）。

FR-5.E2约束命中日志

任何被硬拒绝的投递都必须在通信流水里留痕。

否则用户会以为消息丢了——这比"消息发出去但引发风暴"更难排查。

7.5.3 闸门执行点在哪一层（本方案唯一的架构妥协）

先说问题

NFR-9 要求"硬约束必须落在数据写入口（服务层）"，其反面教材是 team-rooms—— 它的闸门只在工具外壳里，导致命令入口与 Web 入口完全绕过审批。

但 concourse 无法修改官方 ctx.agentTeams 服务， 而跨顶点通信的服务入口在官方手里。因此严格意义上的"服务层闸门"在本方案中不可得。 这一点必须说清楚，而不是假装满足 NFR-9。

可得的执行策略是一个四层收口，覆盖度从高到低：

层手段覆盖对象可绕过性
① toolFilter 收口（主路径） concourse 自己派生的全部子代理。provider 钩子在装配 agentOptions 时， 于 toolFilter.deny 中屏蔽官方 send_message， 只授予 team_send 不可绕过
子代理根本没有那条工具
② 收件箱侧校验 对每一条入站消息，按其 (from, to) 反查开放边集；关闭边上的消息不投递、只入板 不可绕过
与发送方用什么工具无关
③ ctx.tools.guard() 单调拒绝 兜底拦截任何仍能触达官方 send_message 的调用路径（例如 Lead 侧） 仅 deny，无 allow
顺序无法翻案，但需验证对官方 scoped 工具的覆盖效果
④ 全量边归属留痕 所有投递（含被拒）记录 edge 归属与命中约束；在 UI "通信健康度"一行暴露 不可绕过
即便前③层漏了，绕过是可见的
为什么第 ② 层是真正的关键

第 ① 层依赖"子代理只拿到 team_send"这一前提；第 ③ 层依赖 guard 对官方 scoped 注册的实际作用范围。 两者都可能有缝。

而第 ② 层把校验放在"消息进入顶点"这一刻，与发送方是谁、用了什么工具完全解耦—— 它在语义上等价于"服务层闸门"，只是执行位置在收件侧而非发件侧。

→ 设计结论：开放边集的权威判定必须实现在收件箱准入路径上，而不是任何发送工具里。 发送工具只做"早失败"以改善体验，不做安全保证。

设计立场（这句话决定了这一节的边界）

回声风暴不可能被"完全禁止"——合法的协作本来就该有多轮往返。 但它必须是可见的、有上界的、且上界由用户在计划期显式设定。

7.6.1 视觉原语：形状承载语义，颜色加速扫视

P1 原则的落地清单。不使用任何图片、图标字体或 emoji。 每个状态由形状 + 颜色双通道表达——形状是语义的唯一载体，颜色是把扫视速度提上去的并行加速器。

9.3 决议后仍需实测验证的三件事

这些不是"待用户决定"，而是"待工程验证"

① provider 钩子链路能否跑通（R-9）——官方 spawnTeammate 是否忠实把 provider 透传到 concourse 注册的 provider，从而让我们注入 agentOptions。 这是 M1 的第一个验证项。若证伪，退路是自行拉起子代理（放弃复用官方 roster/邮箱，但虚拟拓扑模型与 UI 不受影响）。

② ctx.tools.guard() 对官方 scoped 工具的实际覆盖范围—— 它能否拦住 Lead 侧对官方 send_message 的调用。若拦不住，则第 ① 层 toolFilter 收口必须覆盖到所有非 concourse 派生的顶点， 否则依赖第 ② 层收件箱校验兜底（设计上已经这样安排，此处只是确认兜底是否会被频繁触发）。

③ 宿主并发与深度上限的调整方式——maxActiveSubagents 默认 8、 maxDepth 默认 1。虽然虚拟拓扑的底座深度恒为 1，但 8 个并发顶点对 T2a 仍偏紧， 需确认配置覆盖方式与上限行为（是否 fail-loud）。
