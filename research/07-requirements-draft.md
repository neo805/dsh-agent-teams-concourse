## 1. 论点内核：把"组织架构"变成一等公民

### 1.1 现有插件的根本问题：**把拓扑焊死在实现里**

- `dsh-agent-teams` 的拓扑**常量** = 星型（1 captain + N members，深度 2）
- `dsh-team-rooms` 的拓扑**常量** = 网状（N 对等会话）
- `dsh-subagent-profile` 根本没有拓扑（只有单会话 → 子代理的单边派发）

用户 U-9/U-10/U-11/U-12 的观察切中要害：**真实任务的负责关系图是一个连续谱，而现有插件只提供了两个孤立点。**

### 1.2 形式化：concourse = 带属性的有向图

一个 **concourse（汇流场）** 定义为有向图 `G = (V, E)`：

**顶点 V（执行单元 Executor）**，每个顶点带属性：

| 属性 | 取值 | 作用 |
|---|---|---|
| `id` | 字符串 | 唯一标识（面板/工具里引用） |
| `kind` | `session` \| `subagent` | 是独立会话还是子代理 |
| `role` | 角色标签（自由文本，如 `captain`/`schema-designer`/`security-auditor`） | 语义提示，**不参与权限判定** |
| `model` / `reasoningEffort` | 显式档位 | 见 §4 |
| `toolFilter` | `{allow?, deny?}` | 工具白名单/黑名单 |
| `budget` | `{ tokens?, wallclockMs? }` | 单顶点预算 |
| `lifecycle` | `task` \| `resident` | 任务型（完成即销毁）/ 常驻型（跨任务保留身份与记忆） |
| `contextMode` | `spawn` \| `fork` | 干净上下文 / 继承父上下文 |
| `maxDepth` | 整数 | 该顶点可再派生的最大深度 |

**边 E（通信信道 Channel）**，每条边带属性：

| 属性 | 取值 | 作用 |
|---|---|---|
| `from` / `to` | 顶点 id | 有向 |
| `mode` | `request-reply` \| `notify` \| `board` | 语义 |
| `wake` | `never` \| `on-reply` \| `always` | **是否唤醒对方**（默认 `never`，见 §5） |
| `hopTTL` | 整数 | 该信道允许的最大跳数 |
| `rate` | `{ n, perMs }` | 速率上限 |
| `budget` | `{ tokens? }` | 该信道预算，超额熔断**该边**而非整个团队 |

### 1.3 拓扑谱系：一张图覆盖用户描述的全部形态

| tier | 名称 | 图形 | 典型边集 | 判定条件 |
|---|---|---|---|---|
| **T0** | 单体 | 单点 | `E = ∅` | 任务可在一个上下文窗口内闭环 |
| **T1a** | 单层领队 | 星型 | `∀v≠root: (root→v) ∈ E`，无横向边 | 目标可预先分解为**互不协商**的子任务 |
| **T1b** | 多层领队 | 树（深度≥3） | 父子边 | 目标需**先分层再分解**（子系统各自再拆） |
| **T1.5** | 混合 | 树 + 子树内网状 | 树边 + 某个子树内稠密子图 | **整体需领队，但某子团队内部需协商**（U-10） |
| **T2a** | 多领队并列 | 森林 + 横向边 | 多根，根间有边 | 多个目标各需领队，领队间需互相通报（U-11） |
| **T2b** | 全扁平 | 网状 | 任意连通 | 协作关系**无法预先分解**，需运行中动态产生 |

**关键声明**：这六种形态**不是六个插件功能，而是同一个图模型的不同参数**。`dsh-agent-teams-concourse` 的立论就是：**拓扑是可编辑数据，不是代码常量。**

## 2. 解答 U-8：领队中心式 vs 扁平分布式，真正的判据是什么

用户说"很难区分两者的使用场景"，原因是**现有实现把 5 个本应正交的维度绑死了**：

| 维度 | dsh-agent-teams 的选择 | dsh-team-rooms 的选择 |
|---|---|---|
| D1 **控制权归属** | 中央调度（captain 分配） | 自主认领（成员 claim） |
| D2 **顶点生命周期** | 任务型（完成即销毁） | 常驻型（跨任务保留） |
| D3 **通信拓扑** | 星型 | 网状 |
| D4 **上下文策略** | `spawn`（干净上下文） | 独立会话（天然隔离） |
| D5 **失败恢复** | 中央重派 | 各自重试 |

**这两者被感知为"两个物种"，纯粹是因为每个实现把 5 个维度都选到了同一端。**

真相是每个维度都是独立旋钮，而**真实的组织架构落在 2⁵ 的空间里**。例如：

- **"多层领队 + 子团队内扁平"**（U-10 的原始描述）=
  D1 混合（上层中央、下层自主） + D2 任务型 + D3 树+局部网 + D4 spawn + D5 局部重试
- **"2~3 个总领队并列且互通信"**（U-11）=
  D1 多中心 + D2 任务型 + D3 森林+横向边 + D4 spawn + D5 各自重派

**所以正确的产品动作不是"再做一个插件"，而是"把这 5 个旋钮交还给用户"。**

> 📌 这是本报告对用户 U-8 困惑的直接回答：**领队中心式与扁平分布式不是两个品类，是同一张图上的两种形状。**

## 3. 解答 U-9：tier 决策树

给用户一个可执行的判据（UI 里做成"拓扑建议"的依据）：

```
Q1 任务能否在一个上下文窗口内闭环？
   ├─ 是 → T0 单体（不要组队）
   └─ 否 ↓
Q2 能否在开工前给出完整任务分解，且子任务之间不需要来回协商？
   ├─ 是 ↓
   │   Q2.1 分解结果是否需要再分层（子系统自己还要再拆）？
   │        ├─ 否 → T1a 单层领队
   │        └─ 是 → T1b 多层领队
   └─ 否 ↓
Q3 是否存在"某个子团队内部需要成员协商，但整体仍需领队"的部分？
   ├─ 是 → T1.5 混合
   └─ 否 ↓
Q4 是否存在多个可独立成立的目标，各需自己的领队，但领队间需通报？
   ├─ 是 → T2a 多领队并列
   └─ 否 → T2b 全扁平
```

**建议 UI 直接把这个决策树做成面板上的 5 个单选**（见 §6 线框），并在每次选择时显示"依据"。

## 4. 需求 FR：逐成员模型 / 思考强度 定档（U-5、U-6、U-13）

### 4.1 定档粒度

**每个顶点独立可设**：`model`、`reasoningEffort`、`toolFilter`、`tokenBudget`、`maxDepth`、`contextMode`。
**每个任务（task）独立可设**：`assignee`、`复杂度画像`、`期望产物`。

### 4.2 任务难度画像（7 维）— 自动建议的输入

| 维度 | 取值 | 驱动的档位 |
|---|---|---|
| 认知深度 | 1–5 | `reasoningEffort` |
| 知识广度 | 1–5 | `model` 能力档 |
| 上下文体量 | 估算 token / 文件数 | `model` 上下文窗口 |
| 工具密度 | 预期工具调用轮次 | `tokenBudget` |
| 输出确定性要求 | 低/中/高（可编译、可核验、可复现） | 是否强模型 + 是否强制挂验证者 |
| 风险等级 | 只读/可逆/破坏性/安全敏感 | `toolFilter` + 审批策略 |
| 并行度 | 串行/可并行 | 调度与拓扑 |

### 4.3 建议输出（必须可解释）

```
{
  model: "…",
  reasoningEffort: "…",
  tokenTier: "cheap" | "balanced" | "premium",
  toolFilter: { allow?, deny? },
  maxDepth: n,
  rationale: ["认知深度 4/5：需要多步权衡", "风险等级：安全敏感 → 保留强模型"],
  confidence: 0.0–1.0,
  signals: [...]          // 借鉴 dsh-team-auto-router 的 signals[] 惯例
}
```

### 4.4 三条硬规则

- **FR-4.1 建议可覆盖**：UI 上每个字段可改；改动记录为 `override{ from, to, by }`。
- **FR-4.2 fail-loud 校验**：指定的 model 必须在已注册 provider 目录中；`reasoningEffort` 必须被该 model 支持；越界**直接拒绝**并给出可选值列表，**不静默降级**。（借鉴 `dsh-subagent-profile` 的 fail-loud 哲学）
- **FR-4.3 预设只是快捷填充，不是前提**：预设（preset）用于"一键填入一组常用档位"，但**任何任务都可以完全不用预设而逐字段手动指定**。（直接回应 U-13）

### 4.5 校准闭环（U-6 的长期价值）

- 记录 `建议 → 用户最终采纳值` 的差异，落盘为 `suggestions.jsonl`
- 周期性生成"校准报告"：哪些维度的建议**总是**被上调/下调
- **吸取 dsh-team-auto-router 的教训**（其 README 更新日志记载"阈值 4 下真实任务消息最高仅得 1 分"，后下调为 2）：**启发式阈值必须用真实语料回归**。因此校准闭环不是 nice-to-have，是必需项。

## 5. 需求 FR：通信硬约束（U-7，回声风暴防护）

### 5.1 成因分析

回声风暴 = `唤醒 → 推理 → 回复 → 唤醒对方 → 推理 → …` 的**正反馈**。四个成因：

| 成因 | 说明 | 成本增长 |
|---|---|---|
| C1 **自动唤醒放大** | 收到消息即触发一轮完整推理 | 随跳数线性 |
| C2 **广播放大** | 1 条广播 → N 个顶点各推理一轮并回复 | **随成员数指数** |
| C3 **无终止判定** | 没有"对话已收敛"概念；礼貌性回复本身制造下一轮 | 不收敛 |
| C4 **无预算约束** | 成本事后才可见 | 失控不可逆 |

### 5.2 硬约束清单（分四类，全部为**硬拒绝**而非软警告）

**A. 拓扑类 — 谁能发给谁**
- **FR-5.A1 有向边白名单**：投递前校验 `(from,to) ∈ E`。违反 → **工具调用失败**（不是警告）。**默认边集为空**：未声明即不可通信。
- **FR-5.A2 半双工可选**：`A→B` 不蕴含 `B→A`。请求-应答模式声明为两条边并绑定 `correlationId`。
- **FR-5.A3 跨边界闸门**：跨越团队边界的边需显式声明 + **一次**审批（不是每条消息一次）。

**B. 唤醒类 — 最容易失控处**
- **FR-5.B1 `wake: never` 为默认**：消息进邮箱，**不触发**对方新一轮推理；对方在下一个自然步点读取。
  → 这是**最强的防回声手段**：把事件驱动降级为轮询驱动，从根上消灭互相唤醒。
- **FR-5.B2 唤醒预算**：每顶点每回合窗口最多被主动唤醒 N 次（默认 1）；超出降级为"投递不唤醒"。
- **FR-5.B3 广播降级**：广播**只入共享板，不唤醒任何顶点**。要唤醒必须逐个显式定向。

**C. 终止类 — 怎么算聊完**
- **FR-5.C1 跳数 TTL**：消息携带 `hops` 与 `ttl`；`hops > ttl` → 只记录不投递，板上标记 `HOP_LIMIT`。
- **FR-5.C2 静默判定**：某会话线程连续 K 轮（默认 2）无**新增事实**（纯确认/纯致谢/纯重述）→ 冻结该信道。
- **FR-5.C3 幂等去重**：按 `hash(from|to|correlationId|内容摘要)` 去重；重复投递丢弃并计数。

**D. 预算类 — 成本兜底**
- **FR-5.D1 通道预算**：每条边/每顶点可设 token 预算，超额**熔断该边**（不是整个团队）。
- **FR-5.D2 全局熔断**：concourse 级预算超额 → 暂停所有 `wake ≠ never` 的投递，仅保留人工恢复。

**E. 可观测性（必需，不是可选）**
- **FR-5.E1 回声计数**：统计每条边的 `投递数 / 唤醒数 / 被去重数 / 命中约束数`，在 UI 以一行"通信健康度"呈现。
- **FR-5.E2 约束命中日志**：任何被硬拒绝的投递都要在通信流水里留痕（否则用户会以为消息丢了）。

> **设计立场**：回声风暴不可能被"完全禁止"（合法协作本来就该有多轮往返）。但**它必须是可见的、有上界的、且上界由用户在计划期显式设定**。

## 6. 需求 FR：UI 与信息架构（U-1、U-2、U-3、U-4）

### 6.1 六条设计原则

| ID | 原则 | 具体动作 |
|---|---|---|
| **P1** | **零美术资产** | 插件**不打包任何图片**。禁止头像、emoji 吉祥物、动画精灵。视觉原语只有：Unicode 几何字符、ASCII 树、表格、色块。 |
| **P2** | **决策优先** | 面板最上方永远是"待你决定"，且**通常为空**；空态显式显示 `无待决事项`——让"没有需要我管的事"本身成为可读信息。 |
| **P3** | **单行总览** | 任何时候顶部一行说清团队状态（拓扑/顶点数/活跃数/预算/回声）。 |
| **P4** | **渐进披露** | 过程流水账默认折叠；深度信息按需展开。 |
| **P5** | **一次审批** | 计划审批是**唯一**的常规审批点；运行中零审批，除非越权/破坏性动作。 |
| **P6** | **静态可读** | 颜色**不单独承载语义**（色盲友好，且截图/日志/纯文本转发后仍可读）。 |

### 6.2 视觉原语（纯几何/文字）

**状态符号**（无表情、无图形）：

| 符号 | 含义 |
|---|---|
| `●` | 活跃（正在推理/执行） |
| `○` | 空闲（就绪，等待任务） |
| `◆` | 阻塞（等待决策/依赖） |
| `▸` | 运行中（任务） |
| `✓` | 完成 |
| `✗` | 失败 |
| `·` | 待启动 |
| `─` `│` `├` `└` | 树/连接线 |
| `▰` `▱` | 进度/预算条 |

```
│   A → captain   请求-应答   跳数≤2   速率 3/10min   唤醒 否   [×]
│   captain → A   应答        跳数≤1                   唤醒 否   [×]
│   + 添加边
├──────────────────────────────────────────────────────────────
│ 审批策略   ● 一次批准，运行中零审批
│            ○ 每次跨边界通信确认
│   （1 处需注意：T-4 安全审计使用高风险工具白名单）
└──────────────────────────────────────────────────────────────
```

**每一列的模型/强度都可点开就地修改**（U-5）；默认值是自动建议（U-6）；"依据"列让建议可解释。

## 7. 非功能需求 NFR

## 8. 与现有插件的关系

| 插件 | 关系 | 说明 |

| `dsh-team-auto-router` | **共存 + 分工** | auto-router 负责"**是否进入** concourse"（入口粗筛）；concourse 负责"**进去之后怎么排**"（计划期细排）。两者可同时启用，互不冲突（auto-router 有手势避让与冷却） |

| OQ-1 | 顶层顶点是"独立会话"还是"子代理"？多领队并列（T2a）要求顶点是**独立会话**（子代理无法成为另一个子代理的平级） | 倾向：允许两种顶点混用，但 T2a/T2b 只支持 `session` 顶点 |
